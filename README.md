# PageRank для огромных графов

## 1
PageRank — это алгоритм ранжирования узлов в графе, предложенный в Google для оценки "важности" веб-страниц
Идея: если на вершину ссылаются многие другие, особенно весомые, то она сама становится весомой

## 2. Как работает метрика и зачем нужна
Метрика считает вероятность нахождения серфера на той или иной вершине
Она полезна:
- для анализа социальных сетей (важные пользователи),
- для рекомендаций и анализа графа (социального, знаний, итд)

# 3. Почему выбран PageRank
PageRank универсален:
- простая интерпретация
- хорошо масштабируется для больших графов (вроде как, по крайней мере есть уже методы как это можно делать +- равномерно распределяя нагрузку)
- как мне кажется, его относитьно просто распарраллелить на много тачек, по кайней мере, в отличает от leaderRank
(там groundNode создает) сильную связанность и не позволяет распределить граф по тачкам (мне так кажется), а с pageRank кажется
что возможно наиболеебольшие узлы распределить по разным тачкам, а маленькие поместить на мЕньшем количестве нод чтоб равномерно распределить нагрузку.
С остальными метриками я не придумал как оптимально работать

## 4. Варианты представления графа

1. **Списки смежности (int[][])**
    + Быстрые вычисления
    + Можно порубить на несколько файлов (например .parquet), пометить на разных нодах. Каждая нода будет считывать эти файлы, потом перераспределять
    по вершинам чтоб равномерно распределять рагрузку и минимизировать сетевые походы
    - -- Не помещается в RAM для больших графов, потребует несколько нод для большого графа

2. **Хранение в текстовом файле (edges.txt) + потоковая обработка**
    + Просто реализовать
    – -- Каждая итерация требует повторного чтения с диска, что медленно

3. **Хранение в бинарных чанках с сортировкой по целевым вершинам**
    + Не требуется держать весь граф в памяти
    + Можно параллелить обработку
    + Удобно агрегировать вклад в PageRank через внешний merge-sort  
    -- – Какой-то треш а не код получается и долгие вычисления

## 5. Реализация
В коде реализован подход 3
- исходный граф хранится в `edges.txt` (лист рёбер)
- отдельным проходом строится файл `outdeg.bin` (число исходящих рёбер для каждой вершины)
- итерации PageRank идут так:
    1. читаем `edges.txt`, считаем вклады (`rank[u] / outdeg[u]`) и сохраняем во временные бинарные чанки
    2. чанки сортируются по целевой вершине `v` и мёржатся в новый вектор `rank[v]`
    3. добавляется damping-фактор и масса висячих вершин
    4. проверяется сходимость по l1

Финальный вектор сохраняется в `ranks_final.bin` и в читаемый `ranks_final.txt`.

## 7. Ограничения подхода
- Дисковая нагрузка: каждый шаг требует прохода по всем рёбрам
- Тяжеля логика обработки чанков
- Граф должен быть статичным

## ЗАМЕТКИ

## Партиционирование графа для PageRank
Как мне кажется эта задача лучше всего решается "распилом" графа по различным нодам, а потом аггрегация результатов вычислений каждой ноды на "мастере"
Вот несколько методов распила

### Edge-Cut (разрез рёбер)
- **Суть:** вершины делятся на группы, вместе с их исходящими рёбрами.
- **+:** просто реализуется
- **-:** вершины с огромной степенью создают дисбаланс
- **Можно использовать когда:** графы равномерные без ярко выраженных «супер-узлов»

### Vertex-Cut (разрез вершин)
- **Суть:** рёбра распределяются между партициями, вершины при этом дублируются
- **+:** хорошо балансирует нагрузку при наличии узлов с высокой степенью
- **-:** нужно синхронизировать ранги между копиями вершин
- **Можно использовать когда:** графы с сильным перекосом степеней (например, социальные сети)

### Block/Grid Partitioning (блочное разбиение)
- **Суть:** матрица смежности делится на блоки (подматрицы), каждый блок обрабатывается отдельно
- **+:** упорядоченные коммуникации, подходит для GPU и параллельных систем
- **-:** хуже работает на сильно разреженных графах
- **Можно использовать когда:** регулярные или умеренно разреженные графы, хорошо ложится на распределённые системы

### Streaming / External-Memory (потоковое/внешняя память)
- **Суть:** рёбра хранятся в отсортированных чанках, которые последовательно читаются с диска
- **+:** можно работать на одной ноде (! без сложных технологий и их настроек )
- **-:** несколько проходов по данным, сильная зависимость от скорости I/O, скорее всего медленные вычисления
- **Можно использовать когда:** обработка больших графов на одной машине с ограниченной памятью

---
- Для кластера с «тяжёлыми» узлами лучше подходит **Vertex-Cut**
- Для относительно равномерных графов и MapReduce-подхода — **Edge-Cut**
- Для GPU и блоковых систем — **Block Partitioning**
- Для одной машины и графов, не помещающихся в память — **Streaming/External-Memory**
